Rust Edition · Documentation

Building on DL-ARA.

DL-ARA is a modular Rust workspace for Luma Engine. Every crate has a single responsibility, its own tests, and a documented public API. This page describes what exists today, what each crate does, and what is still in progress.

Introduction

DL-ARA is not a monolith. It is a set of focused crates that build on each other in a shallow dependency graph. The whole workspace is #![forbid(unsafe_code)], and every crate except luma_launcher has zero external dependencies.

The design goal is correctness first, performance measured. Every algorithm is written against a scalar reference first, with tests proving that optimized paths produce bit-identical output. No SIMD until the scalar path is proven. No unsafe anywhere in the foundation crates.

Status

The crates documented on this page are real implementations with passing tests. Research-grade rendering techniques (bidirectional path tracing, photon mapping, ReSTIR, volumetrics) are not implemented and are documented honestly under Limitations.

Getting started

Clone the workspace and build the whole thing:

Terminal Shell

git clone https://github.com/LumaGameEngine/DL-ARA.git

cd DL-ARA

 

# Check the whole workspace

cargo check --workspace

 

# Run tests

cargo test --workspace

 

# Build the launcher

cargo build -p luma_launcher --release

Requires Rust 1.78 or newer (2021 edition). No system dependencies beyond a C toolchain and the Linux windowing libraries that eframe and ureq require.

Math conventions

Every crate above dl-math conforms to the conventions in CONVENTIONS.md. These conventions are normative — violations are bugs, not style issues.

Rule Value Why
HandednessRight-handedMatches wgpu, Vulkan, GLSL
Matrix storageColumn-major, [f32; 16]Matches wgpu and GLSL
Vector conventionColumn-vectors (M * v)Standard math composition order
Camera forward−ZMatches wgpu clip space
Clip-space depth[0, 1]Required by wgpu
Angle unitsRadiansNo degree conversion inside the crate
Deviation from C++

The C++ edition uses [-1, 1] clip depth (OpenGL convention). The Rust edition uses [0, 1] because wgpu requires it. This is documented in CONVENTIONS.md §5. The two editions do not share projection matrices.

dl-math

The scalar foundation. Vectors, matrices, quaternions, colors, fixed-point arithmetic, geometry, noise, and fast math approximations. f32-only, no SIMD, no unions, #[repr(C)] structs.

Key types

  • Vec2, Vec3, Vec4 — 8, 12, and 16 bytes respectively. Hand-written reverse-scalar-multiply impls. Bit-identical Hash implementations.
  • Mat4 — column-major flat [f32; 16]. inverse() and look_at() return Option instead of producing NaN.
  • Quat — Hamilton multiplication, slerp with antipodal handling.
  • Color — full HSV / luminance / tonemapping / blend / packing surface.
  • Fixed<IntType, BITS> — fixed-point with a sealed trait. sqrt uses bit-by-bit isqrt.
  • Aabb, Ray, Plane, Frustum — geometry primitives. is_point_in_triangle uses an inclusive boundary.
example.rs Rust

use dl_math::{Mat4, Vec3, Vec4};

 

// Column-major, column-vectors

let m = Mat4::translation(Vec3::new(1.0, 2.0, 3.0))

    * Mat4::rotation_y(0.5);

 

let p = Vec4::point(Vec3::new(0.0, 0.0, 0.0));

let world = m * p;

 

// Singular matrices return None, not NaN

let inv = m.inverse().unwrap();

dl-rasterization

A CPU software rasterizer with three interchangeable pipelines: serial, tiled, and parallel. All three produce bit-identical output — the tiled and parallel tests assert this against the serial reference.

Pipelines

  • Serial — single-threaded bounding-box scan. The reference implementation.
  • Tiled — 16×16 tiles, bin triangles into tile lists with a prefix-sum layout, then process each tile with cache locality.
  • Parallel — the same tiled pipeline, dispatched across N threads with an atomic tile cursor. No locks, no per-pixel contention (each tile owns its pixels).

Coverage

  • Fixed-point subpixel coordinates (8 fractional bits, 1 pixel = 256 units).
  • Watertight edge equations with incremental step_x / step_y.
  • Top-left fill rule with per-edge flags.
  • Perspective-correct interpolation with pre-divided barycentrics.
  • Depth buffer with Less, LessEqual, Greater, GreaterEqual, and Always (standard and reversed Z).

dl-ray

The geometric foundation for ray-based rendering. Watertight triangle intersection, analytic primitives, and a binned SAH BVH.

Intersection

  • Watertight Möller–Trumbore (Woop, Benthin, Wald 2013) — no dropped rays along shared edges.
  • Ray stores precomputed inv_direction for fast slab tests.
  • Hit has a front_face flag and flips its normal automatically when the ray hits from inside.
  • Analytic primitives: Plane, Sphere, Disk, Cylinder, Cone.

BVH

  • Binned Surface Area Heuristic with 12 buckets per axis.
  • Iterative traversal with an explicit [u32; 64] stack — no recursion, so malicious geometry cannot overflow the stack.
  • Closest-hit descends into the nearer child first; any-hit returns on the first intersection.
  • refit() for dynamic meshes — updates node AABBs without re-sorting the tree.
trace.rs Rust

use dl_ray::{Ray, Scene, Triangle};

 

let scene = Scene::new(vec![

    Triangle::new(

        Vec3::new(0.0, 0.0, -3.0),

        Vec3::new(1.0, 0.0, -3.0),

        Vec3::new(0.0, 1.0, -3.0),

    ),

]);

 

let ray = Ray::new(Vec3::ZERO, Vec3::new(0.25, 0.25, -1.0));

 

if let Some(hit) = scene.intersect(&ray, 0.0, f32::INFINITY) {

    println!("hit at t={} normal={:?}", hit.t, hit.normal);

}

dl-ray-tracing

A real-time path tracer. One sample per pixel per frame, with temporal accumulation and an à-trous denoiser. Not an offline renderer — the temporal + denoise stack is what makes 1 spp usable.

What's implemented

  • Reference-correct PCG32 with per-pixel-per-frame seeding for TAA.
  • Sampling: hemisphere-uniform, cosine-weighted, sphere-uniform, GGX reflection. Every distribution has a Monte Carlo PDF integration test.
  • Bsdf trait with Lambertian, Mirror, Dielectric (verified to reflect ~4% at normal incidence into glass), and Emissive.
  • Lights: point, directional, and area (uniform triangle sampling).
  • Path tracer with NEE (next-event estimation), Russian roulette, and power-heuristic MIS on both sides.
  • Temporal accumulation (exponential moving average) and a real à-trous denoiser driven by depth and normal.
  • ACES / Reinhard / Clamp tonemapping and sRGB encode.
  • render_realtime pipeline: trace → temporal → denoise → tonemap → sRGB → u8.
Not yet on target

The path tracer does not yet hit the target of 60 fps at 720p / 45 fps at 1080p / 30 fps at 1440p on current hardware. The architecture is correct (1 spp, temporal, denoise, tile-parallel); tuning work remains on light selection and BVH traversal.

dl-rendergraph

The CPU render graph. Target pooling, typed handles, and pass scheduling with dependency resolution.

Components

  • dl-render-graph-compile — dependency resolution (RAW / WAR / WAW), cycle detection, stable topological sort. Pure graph logic, no rendering.
  • dl-render-pass — the RenderPass trait, PassDescriptor, PassContext, and ResourceAccess.
  • dl-rendergraph — the actual graph. Owns the target pool, executes the compiled pass list, and produces the final image.
Alpha status

dl-rendergraph is Alpha. It powers the neon-grid demo, but the API is still evolving. The two foundation crates it depends on are stable.

dl-render-camera

A camera and projection system designed for large world coordinates. Position and forward direction are stored in f64 and only downcast to f32 when producing matrices for the GPU.

Why f64?

A camera at x = 1e6 in a f32 world produces visible jitter in the view matrix, because f32 has ~0.06 unit precision at that magnitude. Doing the subtraction (center - eye) in f64 and then downcasting avoids the jitter entirely.

  • Camera — f64 position and forward, produces f32 matrices.
  • Projection — perspective and orthographic, both using [0, 1] clip depth.
  • Frustum — six-plane extraction (Gribb-Hartmann, adapted for [0, 1]) for culling.
  • Viewport — integer pixel rectangle, top-left origin.

dl-input

Unified input mapping across keyboard, mouse, and gamepad. Xbox, PlayStation, and Nintendo controllers are all translated to a single gamepad layout by GamepadButton::from_platform(controller, physical_face).

Actions

  • InputBinding with scale, invert, and deadzone.
  • InputAction with binary, 1D, and 2D variants.
  • Radial deadzone for sticks with rescale; independent axis deadzone for triggers.
  • ActionMap with WASD and arrow-key bindings built in.
  • Input::end_frame() must be called at the end of every frame to clear the pressed / released flags.
input.rs Rust

use dl_input::{ActionMap, Input, events::InputEvent, keyboard::Key};

 

let mut input = Input::new();

let mut actions = ActionMap::new();

 

actions.bind_key("Jump", Key::Space);

actions.bind_wasd_movement("Move");

 

input.process_event(InputEvent::KeyDown(Key::Space));

input.update(0.016);

actions.update(&input);

 

if actions.is_action_pressed("Jump") {

    // ...

}

 

input.end_frame();

actions.end_frame();

luma_launcher

A native launcher and auto-updater for the Rust edition. Queries GitHub Releases, downloads the platform-specific archive, verifies SHA256, extracts, and launches the engine as a child process.

Update flow

  1. Query api.github.com/repos/{owner}/{repo}/releases/latest.
  2. Find the LATEST.json asset and parse the manifest.
  3. Compare the version against the installed one (semver).
  4. Download the platform archive to a temporary file, hashing as it streams.
  5. Verify SHA256 against the manifest.
  6. Extract to a staging directory.
  7. Rename the running engine to engine-old, move the new engine into place, then spawn it.
  8. When the child exits, delete engine-old.
Requires a release pipeline

For the auto-updater to work, the GitHub repository must publish releases with LATEST.json and the platform archives. The exact asset naming is documented in the launcher's README.md.

Limitations

Being honest about what is not done is as important as documenting what is. Known limitations of the Rust edition as of this writing:

Rendering

  • Path tracer does not yet hit the target framerate. The architecture is correct; tuning remains.
  • No bidirectional path tracing, photon mapping, ReSTIR, or volumetrics. These are research-grade integrators, each a multi-month effort. They will be added to the workspace only when their foundations and tests are real.
  • No spectral rendering. The path tracer works in RGB, not wavelengths.
  • No subsurface scattering or BSSDFs. Materials are Lambertian, mirror, dielectric, and emissive only.
  • Temporal reprojection assumes a stationary camera for now. Moving-camera reprojection will be added when the engine has a moving camera.

System

  • No GPU backend. All rendering is CPU-only by design.
  • No networking. The launcher uses HTTP only to check for updates.
  • No scene serialization yet. Projects are not saved to disk in the Rust edition.
  • No editor. The Rust edition ships a launcher, not an editor. The engine can be driven programmatically or through custom binaries.

Platforms

  • Linux is the primary target. The launcher builds on macOS and Windows, but the render and trace pipelines have been tested primarily on Linux x86_64.
  • ARM (Apple Silicon, aarch64 Linux) should work but has not been extensively tested.
Alpha software

The Rust edition is early. Do not build a commercial product on it without tracking the workspace's development closely. The foundation crates (dl-math, dl-ray, dl-rasterization) are stable; the higher layers are still in motion.
