C++ Edition · Documentation

Building on Luma Engine C++.

Everything you need to understand, build, and extend the C++ edition of Luma Engine. Written against the current v0.1.0-alpha build. If something here is a roadmap promise rather than a shipped feature, it will say so explicitly.

Introduction

Luma Engine C++ is a compact, CPU-first game engine written in modern C++20. It ships with an integrated editor, a software rasterizer, a custom scripting language, and a scene graph. It runs on Linux today; Windows and macOS are on the development path.

It is deliberately not a general-purpose engine. It targets a specific kind of project: games that value simplicity, deterministic behaviour, and low hardware requirements. If you want a hardware-accelerated renderer with a million third-party extensions, this is not it — and that's the point.

Status

Everything documented in this page is implemented and shipping in v0.1.0-alpha. Items that are planned but not yet present are marked under Current limitations.

System requirements

The C++ edition is CPU-only. No dedicated GPU required. The engine compiles on Linux natively; cross-platform builds require further development.

Building from source

The C++ edition builds with CMake. All third-party dependencies (SDL3, Dear ImGui, stb_image) are vendored in the repository — you don't need to install anything globally.

Terminal Shell

# Clone the repository

git clone https://github.com/LumaGameEngine/Luma_Engine.git

cd Luma_Engine

 

# Configure with CMake

mkdir build && cd build

cmake ..

 

# Build (uses all cores)

make -j$(nproc)

The first build takes a few minutes because it compiles SDL3 and ImGui from source. Subsequent builds are incremental.

Runtime loop

The runtime runs the main game loop at a target of 60 FPS. Each frame:

  1. Poll SDL3 events into the InputManager.
  2. Update the scene graph (propagate transforms).
  3. Execute up to 100 LOVE VM instructions (the instruction budget).
  4. Render the current frame through Dimension L.
  5. Swap buffers via SDL3.

The instruction budget exists so that a script cannot starve the editor's UI or the renderer. If your script needs more than 100 instructions per frame, it is doing too much; break it into smaller state updates.

Why a budget?

An unbounded script could lock the editor. The budget is a hard limit — if a script exceeds it, the runtime pauses the VM and reports the overrun in the editor's console. This is intentional, not a bug.

LOVE scripting

LOVE (Luma Object & Virtual-machine Environment) is the C++ edition's scripting language. It compiles to bytecode and runs on a stack-based VM. See the LOVE language reference for the full instruction set and syntax.

The VM lives in src/love/ and exposes its API to the editor and the game runtime. It is sandboxed — scripts cannot access raw memory or filesystem APIs.

game.love LOVE

let score 0

let x 433

let y 285

 

loop

  color 20 20 40

  clear

  // Game logic here

  present

end

Dimension L

Dimension L is the rendering technology inside the C++ edition. It is a software rasterizer — every pixel is computed on the CPU. This is the architectural choice that lets the engine run without a dedicated GPU.

DL-V1 architecture

The current version of Dimension L is called DL-V1. It provides:

  • A framebuffer with a Z-buffer for depth testing.
  • Primitive drawing: pixel, line, triangle, rectangle, and circle (outlined and filled).
  • A camera system with view and projection matrices.
  • Colour management with per-primitive colour setting.
  • A viewport that maps to the editor's render panel or the full window.

Render graph

Dimension L supports a lightweight render graph. Passes declare reads and writes against named targets, and the graph resolves execution order. The current implementation is deliberately minimal — there is no automatic barrier insertion because there is no GPU to barrier.

Scene system

The scene graph is a tree of nodes. Every node has a local transform and a computed world transform. When a node's local transform changes, its world transform and those of all descendants are marked dirty and recomputed on the next frame.

SceneNode.hpp C++

class SceneNode {

public:

  Vec3 position;

  Vec3 rotation;

  Vec3 scale{ 1, 1, 1 };

 

  Mat4 WorldTransform() const;

  void AddChild(std::unique_ptr<SceneNode> child);

 

private:

  std::vector<std::unique_ptr<SceneNode>> m_children;

  SceneNode* m_parent{ nullptr };

};

Two concrete node types ship today: SpriteNode (a textured quad) and ShapeNode (a primitive with a colour). Both derive from SceneNode.

Editor

The editor is built on Dear ImGui with docking support. It provides:

  • A viewport that renders the current scene through Dimension L.
  • A LOVE script editor with syntax highlighting.
  • A file and asset browser.
  • A property panel for the selected node.
  • A launcher screen for opening or creating projects.
  • A console for VM output and error reporting.
The editor is the launcher

There is no separate launcher binary in the C++ edition. The editor opens to a launcher screen, and from there you create or open a project. The Rust edition uses a separate launcher binary — see the Rust edition for that architecture.

Asset pipeline

The AssetManager handles loading, caching, and reference counting for textures. Supported formats today:

  • PNG — via stb_image.
  • JPG — via stb_image.
  • WAV — via SDL3 audio.

Assets are identified by a UUID and cached by UUID. When a file on disk changes, the asset is marked dirty and reloaded on the next access.

Input

Input is provided by SDL3 and routed through the engine's InputManager. Two paths are available:

  • Polling — the runtime checks key states each frame. Used internally by LOVE's key_down instruction.
  • Events — keyboard and mouse events are pushed to the editor and to registered listeners.

Gamepad support is not yet implemented. See Current limitations.

Audio

The audio system uses SDL3's audio backend. It supports:

  • Loading WAV files into named channels.
  • Playing, pausing, and stopping a channel.
  • Setting master volume.
  • Per-channel volume (via the channel ID).
audio.love LOVE

audio_load "pop.wav" "pop"

audio_play "pop"

audio_set_volume 0.5

Audio is not spatialised. It plays through the default output device. Spatial audio is under consideration but not implemented.

Current limitations

Being honest about what is not done is as important as documenting what is. The following are known limitations as of v0.1.0-alpha:

  • Linux only. Windows and macOS builds are planned but not shipped. The code compiles on Linux; the SDL3 and CMake configurations are Linux-centric.
  • No hardware acceleration. Dimension L is a software rasterizer. This is a design choice, not a limitation, but it means the engine will not match the performance of GPU-based engines on large scenes.
  • No gamepad support. Keyboard and mouse only in this version.
  • No networking. Single-player only.
  • No 3D rendering. Dimension L currently ships a 2D-oriented rasterizer. 3D primitives (triangles in 3D space, perspective-correct textures) are not implemented.
  • No animations. Sprite animation is on the roadmap but not implemented.
  • No particle system. Not implemented.
  • No physics. LumaX is a separate project; see the homepage for its status.
  • Limited asset formats. PNG, JPG, and WAV only. OGG, MP3, and sprite sheets are not supported yet.
  • No scene serialization to disk. Projects can be created and edited but not yet saved.
Alpha software

The C++ edition is v0.1.0-alpha. It is functional but not production-ready. Do not use it for a commercial project without expecting to track the engine's development closely.
