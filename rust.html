Overview

A workspace, not a monolith.

The Rust edition is built as a set of focused crates. Each crate has a single responsibility, its own tests, and a documented public API. The workspace is designed so that new rendering techniques can be added without destabilising the ones that already work.

Crates

What DL-ARA ships today.

Every crate below is real. Each one has tests that pass. Statuses reflect where each crate currently sits, honestly.

Math foundation

dl-math

Vectors, matrices, quaternions, colors, fixed-point, geometry, noise, and fast math approximations. No SIMD, no `unsafe`, `f32`-only, documented conventions.

Stable

Software rasterization

dl-rasterization

Watertight edge equations, top-left fill rule, subpixel precision, depth buffer, serial / tiled / parallel rasterizers. Tiled and parallel outputs are bit-identical to serial.

Stable

Ray tracing foundation

dl-ray

Watertight Möller–Trumbore triangle intersection, analytic primitives, binned SAH BVH build, iterative traversal, refit for dynamic meshes.

Stable

Real-time path tracer

dl-ray-tracing

PCG32 with per-pixel-per-frame seeding, cosine / GGX sampling with PDF tests, NEE with power-heuristic MIS, Russian roulette, temporal accumulation, à-trous denoiser.

Render graph

Target pool, typed handles, RAW/WAR/WAW dependency extraction, cycle detection, stable topological sort. The neon grid renderer consumes it.

Input and camera

Architecture

Built from the ground up.

The dependency graph is deliberately shallow. Every crate depends only on crates below it. This is what makes the workspace extensible without becoming fragile.

DL-ARA — Crate dependency graph

luma_launcher // downloads + runs the editor

  └── dl-ray-tracing // real-time path tracer

      ├── dl-ray // BVH + watertight Möller–Trumbore

      │   └── dl-math // vec, mat, quat, color, noise

      └── dl-math

 

dl-rendergraph // neon grid renderer

  ├── dl-render-graph-compile // dependency resolution + topo sort

  ├── dl-render-pass // pass trait + context

  └── dl-math

 

dl-rasterization // software rasterizers

  └── dl-math

 

dl-render-camera // f64 camera at any scale

  └── dl-math

 

dl-input // keyboard, mouse, gamepad

  └── (no dependencies)

 

dl-math // no dependencies

Design principle

Every crate in DL-ARA is #![forbid(unsafe_code)] with zero external dependencies except for the launcher (which uses ureq, sha2, flate2, tar, zip, and eframe). Nothing in the foundation stack pulls in a graphics API, a web framework, or an async runtime.

Philosophy

Correctness first. Performance measured.

Every algorithm in the Rust edition is written against a scalar reference first. Optimizations are introduced only when profiling shows they matter, and only after a determinism test proves the optimized path produces bit-identical output to the reference.

The tiled rasterizer is bit-identical to the serial one. The parallel rasterizer is bit-identical to the tiled one. The path tracer's PDF integration tests prove the sampling distributions are correct before any image is rendered.

No SIMD until the scalar path is proven. No `unsafe` anywhere in the foundation crates. No fake code — modules that would be stubs stay out of lib.rs until they contain real implementations.

The convention document (CONVENTIONS.md) in dl-math defines the coordinate system, matrix storage order, camera conventions, and clip-space depth range. Every crate above dl-math conforms to those conventions, which is why the pieces compose without silent bugs.
